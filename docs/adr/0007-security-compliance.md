# ADR 0007 — Security and compliance (encryption, redaction, signatures, sanitize, audit)

Status: accepted

## Decisions
- **Everything runs on the user's device** (`@pdfsuite/security`, TypeScript). The only server part is the audit trail endpoint. Documents and certificate keys never leave the machine.
- **Encryption**: own implementation of the PDF standard security handler. *Write*: AES-256 (revision 6, ISO 32000-2) only — the modern, non-deprecated option; permissions as P flags. *Read*: RC4-40/128, AES-128, AES-256 (R2–R6), including object streams, so old files open. Crypto primitives are small and verified (AES against node:crypto + FIPS-197; MD5/RC4/SHA against vectors); no new runtime dependency. A raw-PDF syntax layer (`pdfsyntax.ts`) parses/writes objects because pdf-lib cannot read encrypted files.
- **The working copy is decrypted in memory**; the app re-encrypts on every PDF it writes (`deliver`). Opening with only the *user* password applies the permissions in the UI (annotate/forms/page tools/copy/convert are disabled); the owner password lifts them. Re-saving a file opened without the owner password keeps the user password and permissions and uses a random owner password (the owner password cannot be recovered from the file).
- **Sanitize/examine** (pdf-lib): metadata + XMP, JavaScript/launch/URI actions, attachments, comments, links, bookmarks, thumbnails, private data, optional form flatten; orphaned objects are pruned so removed data does not linger. The examiner reports earlier incremental revisions (deleted content may still be inside) — a full rewrite removes them.
- **Redaction removes content, it does not paint over it**: content streams are parsed and rewritten (per-glyph removal with kerning compensation for text, including invisible OCR text; image pixels blanked or the image dropped; small vector shapes dropped; form XObjects copied-on-write; covered annotations/widgets and their `/AP`, `/V` removed), then a cover rectangle is drawn and unreferenced objects are pruned. Verified by extracting text with PDF.js/PDFium/pikepdf afterwards. Marks are normal `/Redact` annotations until applied (undoable, saved in the file), created by text selection, area drag, or **pattern search** (SSN, email, phone, Luhn-checked cards, IBAN, dates, words, custom regex).
- **Signatures**: CAdES-style detached CMS (`ETSI.CAdES.detached`, SHA-256 + RSA, ESS signing-certificate-v2) written as an **incremental update** (xref table or xref stream, matching the file), with optional visible appearance. The verifier checks digest, signature, certificate validity at signing time, trust against a user-managed root list, and whether the signed range covers the whole file; status is valid / valid-untrusted / modified-after-signing / invalid. Independent oracle: **pyHanko** validates our output (intact, valid, ModificationLevel.NONE), including multiple signatures and tampered files. node-forge (BSD-3-Clause OR GPL-2.0, used under BSD) does the ASN.1/X.509/PKCS#12 work.
- **Signing safety rails**: edits that rewrite the file warn first when it is signed (any rewrite invalidates signatures); plain saves of an untouched file keep bytes as they are; signing is refused while password protection is pending (we do not combine signing and encryption).
- **Audit log**: hash-chained entries (`seq`, time, user, action, document SHA-256, details, `prev`, `hash`) in browser storage with verification and CSV export (formula-injection safe); each entry is also forwarded to **`POST /v1/audit`**, where the server assigns time/sequence/hashes (authoritative, JSON-lines persisted, admin-only `GET /v1/audit` and `/verify`). Details are limited to scalars; document names are reduced to the base name; the server records every job submission itself.

## Verification
- `@pdfsuite/security`: 65 tests — crypto vectors; qpdf-generated RC4/AES fixtures decrypted and compared; our AES-256 output accepted by qpdf/pikepdf, PDFium and PDF.js (250-run stress that found and fixed a 2.B round-termination bug); sanitize; redaction (text, kerning, rotated, images, forms, annotations, hidden text) with extraction checks; signing and verification against pyHanko; audit chain tamper detection.
- `@pdfsuite/api`: 22 tests incl. audit endpoints (roles, persistence, tamper detection after restart). `@pdfsuite/viewer`: 21 tests incl. pattern matching.
- Browser run: password prompt (wrong then right password, lock shown, copy/convert restricted), find-and-redact "brown fox" on 5 pages (text gone, rest intact), sign with a test certificate → Signatures shows "intact, signer not trusted" → audit log chain intact, sanitize.

## Known limitations / follow-ups
- Signing is RSA only; no OCSP/CRL/timestamp (no LTV), no certificate-based (public-key) encryption, no hardware tokens/PKCS#11, no PDF/A-style archival signatures. Trust is a manual root list (no OS/AATL store).
- Redaction heuristics: vector paths larger than the redaction are kept; shadings (`sh`) are not removed; soft-masked images are removed whole; a glyph goes if ≥20% of it is covered (marks are padded 0.75 pt); vertical writing ignored; custom CMaps assumed 2-byte. Mark rectangles for found text come from text-run positions measured with canvas fonts, so always review marks; scanned (image-only) pages need OCR first for pattern search.
- Permissions are advisory in other software and enforced only by this app's UI; AES-256 R6 resists offline guessing only as far as the password is strong.
- The local audit trail can be cleared by whoever controls the browser profile; truncation is detectable only against the server copy. Dev StrictMode may log `document.open` twice.
- RC4/AES-128 *writing* is intentionally not offered. Encrypted files using public-key handlers cannot be opened.
